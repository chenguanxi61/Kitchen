## 一、论文建议目录

### 摘要
- 研究背景：Unity 在游戏开发与教学实践中的广泛应用，多人协作玩法对实时交互和状态一致性提出更高要求。
- 研究目标：设计并实现一款基于 Unity 的多人协作烹饪游戏，完成从场景切换、角色交互、食材加工到订单交付的完整闭环。
- 关键技术：Unity、C#、ScriptableObject、Netcode for GameObjects、事件驱动、模块化设计。
- 实现结果：完成主菜单、房间准备、角色进入游戏、订单生成、切菜、烹饪、装盘、送餐、计时与结算等核心功能，并实现基础联机同步。
- 结论：系统具备较好的演示性、可扩展性和工程实践价值，但在网络一致性和测试覆盖方面仍有进一步优化空间。

### 第二章 需求分析
#### 2.1 系统目标
- 系统目标是实现一款支持 2 至 4 名玩家进行协作操作的厨房烹饪游戏。
- 玩家在限定时间内根据订单要求完成食材处理、装盘和交付任务，以获得更高完成度和更好的游戏体验。

#### 2.2 业务流程分析
- 业务主流程建议写成：
  1. 玩家从主菜单进入房间场景。
  2. Host 创建房间，客户端加入。
  3. 玩家准备完毕后进入游戏场景。
  4. 系统生成订单并开始倒计时。
  5. 玩家在不同柜台之间协作完成取材、切配、烹饪、装盘。
  6. 玩家将成品提交到交付台，系统判定是否匹配订单。
  7. 到达限定时间后进入结算界面。
- 如果老师要求画图，这一节适合配业务活动图或泳道图。

#### 2.3 功能需求分析
##### 2.3.1 场景与流程控制需求
- 支持主菜单、房间场景、角色选择场景、加载场景和游戏场景之间的切换。
- 支持多人准备与统一进入游戏。
- 支持游戏开始倒计时、游戏进行计时和结算。

##### 2.3.2 玩家交互需求
- 玩家能够移动、朝向交互对象并执行交互操作。
- 玩家能够拾取、放置、传递和丢弃厨房对象。
- 玩家能够针对不同柜台执行主交互与辅助交互。

##### 2.3.3 厨房对象处理需求
- 系统应支持容器柜台生成食材。
- 系统应支持切菜台对食材进行阶段性加工。
- 系统应支持炉灶对食材进行烹饪与烧焦状态切换。
- 系统应支持盘子装配多种食材。

##### 2.3.4 订单与交付需求
- 系统应能够周期性生成待完成订单。
- 系统应根据盘中食材与订单配方进行匹配判定。
- 系统应区分正确交付与错误交付，并提供对应反馈。

##### 2.3.5 用户界面需求
- 系统应展示订单列表、进度条、倒计时、暂停界面和结束界面。
- 系统应在交互发生时提供必要的视觉与音效反馈。

##### 2.3.6 联机协作需求
- 系统应支持 Host 建房、客户端加入和统一开局。
- 系统应支持关键厨房对象生成、销毁及状态更新的同步。
- 系统应支持部分交互流程在服务器权威下完成。

#### 2.4 非功能需求分析
##### 2.4.1 可用性需求
- 操作方式应清晰，交互反馈应及时，界面信息应直观。

##### 2.4.2 实时性需求
- 对于订单刷新、交付判定、烹饪进度等关键流程，系统应具备较好的实时响应能力。

##### 2.4.3 稳定性需求
- 系统应保证核心玩法闭环完整运行，避免因联机状态不同步导致核心流程中断。

##### 2.4.4 可扩展性需求
- 系统应便于新增菜谱、食材、交互对象和界面表现。
- 配方和食材配置不应硬编码在业务流程中，应通过数据对象管理。

#### 2.5 用例分析
- 主要参与者可写为“玩家”和“系统”。
- 玩家用例建议包括：
  - 创建房间
  - 加入房间
  - 准备开始
  - 控制角色移动
  - 拾取食材
  - 切配食材
  - 烹饪食材
  - 装盘
  - 提交菜品
  - 暂停游戏
- 系统用例建议包括：
  - 加载场景
  - 生成订单
  - 判定交付结果
  - 统计游戏状态

#### 2.6 数据与对象分析
- 可将“数据建模”改写为“对象与数据模型分析”，避免写成传统数据库设计。
- 核心对象建议写为：
  - 玩家对象 Player
  - 订单对象 RecipeSO
  - 食材对象 KitchenObjSO
  - 厨房实体对象 KitchenObj
  - 盘子对象 PlateKitchObj
  - 柜台对象 BaseCounter 及其子类
- 关系描述建议：
  - 一个订单包含多个食材需求。
  - 一个盘子可组合多个食材对象。
  - 一个厨房对象可附着在玩家或柜台上。
  - 不同柜台对厨房对象执行不同处理逻辑。

### 第三章 系统设计
#### 3.1 系统总体设计
- 系统采用 Unity 引擎进行开发，使用 C# 编写核心逻辑。
- 联机架构采用 Host 模式，Host 同时承担服务器和本地客户端职责。
- 核心流程遵循服务器权威思想，由 Host 负责关键交互判定、对象生成与订单管理。

#### 3.2 架构分层设计
##### 3.2.1 表现层
- 负责场景显示、角色动画、UI 展示、进度条显示、音效与视觉反馈。
- 对应项目中的 UI 脚本、动画控制脚本、柜台视觉脚本等。

##### 3.2.2 逻辑控制层
- 负责游戏状态机、订单管理、玩家交互、物品加工和交付判定。
- 可重点对应 `GameManager`、`DeliverManager`、`Player`、各类 `Counter`。

##### 3.2.3 网络通信层
- 负责玩家连接、场景同步、网络对象生成与销毁、关键状态广播。
- 可重点对应 `KitchGameMultiPlayer`、`ServerRpc`、`ClientRpc`、`NetworkVariable`。

#### 3.3 核心模块设计
##### 3.3.1 游戏状态管理模块
- 以 `GameManager` 为核心，控制等待开始、开始倒计时、游戏进行和游戏结束等状态。
- 负责暂停与恢复逻辑，并为 UI 提供状态通知。

##### 3.3.2 联机管理模块
- 以 `KitchGameMultiPlayer` 为核心，负责 Host 启动、客户端加入、玩家准备状态记录、场景切换和玩家对象生成。
- 这一节重点体现多人协作的工程实现价值。

##### 3.3.3 玩家交互模块
- 以 `Player` 为核心，实现角色移动、朝向控制、碰撞检测、交互目标选择和交互输入响应。
- 说明主交互与辅助交互的设计思路。

##### 3.3.4 柜台加工模块
- 以 `BaseCounter` 为抽象基类，派生出 `ContainerCounter`、`CuttingCounter`、`StoveCounter`、`PlatesCounter`、`TrashCounter`、`DeliveryCounter` 等子类。
- 强调不同柜台职责明确，便于后续扩展。

##### 3.3.5 订单与交付模块
- 以 `DeliverManager` 为核心，负责待完成订单生成、订单队列维护、交付结果判定和结果反馈。

##### 3.3.6 UI 显示模块
- 包括主菜单、暂停界面、结束界面、订单列表、订单单项、盘子图标、进度条和倒计时显示等。
- 说明 UI 与逻辑模块之间通过事件或状态接口进行协作。

#### 3.4 数据驱动设计
- `RecipeSO` 用于定义订单配方。
- `KitchenObjSO` 用于定义食材与厨房对象的数据资源。
- `CuttingRecipeSO`、`FryRecipeSO`、`BurningRecipeSO` 用于定义加工链路。
- 这一节要强调 ScriptableObject 对配置解耦和扩展维护的价值。

#### 3.5 网络同步设计
- 对象生成与销毁由服务器侧发起，再同步到客户端。
- 订单生成通过 RPC 广播到各端。
- 炉灶状态和进度通过 `NetworkVariable` 进行同步。
- 玩家准备状态通过服务器记录并决定是否切换场景。
- 这部分要写“实现了基础联机框架与关键交互同步”，不要夸大为完整高一致性网络系统。

#### 3.6 界面与交互设计
- 主菜单负责进入房间流程。
- 房间/角色选择阶段负责完成联机前准备。
- 游戏内界面负责展示订单、倒计时、进度与结果反馈。
- 暂停和结算界面负责辅助用户完成游戏流程。

### 第五章 系统测试
#### 5.1 测试环境
- 建议写明 Unity 版本、运行平台、测试方式和网络测试基本环境。
- 可直接引用项目实际版本：Unity 2022.3.62f3c1。

#### 5.2 功能测试
- 主菜单进入房间是否正常。
- 玩家移动与交互是否正常。
- 食材生成、切菜、烹饪、装盘、丢弃是否正常。
- 订单生成与交付判定是否正常。

#### 5.3 联机测试
- Host 创建房间，客户端加入是否成功。

- 多端是否能看到关键厨房对象状态变化。
- 交付成功与失败是否能正确反馈。

#### 5.4 异常与边界测试
- 错误配方提交时系统反馈是否正确。
- 玩家空手交互时系统是否稳定。
- 同一对象被多次交互时是否出现异常状态。
- 游戏结束后是否能正确停止主要流程。
